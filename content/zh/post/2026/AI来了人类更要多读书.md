## <span class="section-num">1</span> 前言 {#前言}

距离我写的《[杂谈AI取代程序员](https://ramsayleung.github.io/zh/post/2025/%E6%9D%82%E8%B0%88ai%E5%8F%96%E4%BB%A3%E7%A8%8B%E5%BA%8F%E5%91%98/)》已经过去一年半, 再分享一下我对AI的个人感悟。

先说下我自己AI的使用和熟悉程度，我司的风格是做淘金热里卖铲子的人, 而我自己从2024年就在 S3 参与AI相关功能的开发，主要是做面向AI的海量训练数据存储，现在 Anthropic 也在用我们组的产品。

工作中，我们可以使用的是 Anthropic 部署在 AWS 上的最新模型(当前是 Opus 4.7)，量大且绝对管够; 而工作之外我也订阅了Google的 Gemini Pro 以及 ChatGPT 的 Business Plan, 可以说御三家的模型我都尝到饱。


## <span class="section-num">2</span> 思考快与慢 {#思考快与慢}

当我和朋友聊起AI的时候，他说他已经用了几个月的 Claude Code, 现在 Claude Code 写出来的代码他已经不想看了；不过好几次 Claude 搞不出来的功能，只能自己下手写 design 教它怎么搞；但是代码的确已经不想看了，更何况自己动手写代码。

其实这种现象在日常生活中也很常见，短视频看多了之后就无法看长视频；电影解说看多了之后也没法完整看完一部电影；
读书视频看多了之后，也不会真的去读一本书了，甚至一篇长文都看不下来。

有一本著名的心理学的书叫《[思考，快与慢](https://book.douban.com/subject/10785583/)》，作者就把人类的思维归纳为两个思考模式：

系统一快速、直觉且情绪化，系统二较慢、较具计划性且更仰赖逻辑。

但系统一也很容易上当，它固守「眼见即为事实」的原则，任由损失厌恶和乐观偏见之类的错觉引导我们作出错误的选择。
有意识的系统二通过调动注意力来分析和解决问题，并作出决定，它比较慢，不容易出错，但它很懒惰，经常走捷径，
直接采纳系统一的直觉型判断结果。

用多了系统一，就很难激活系统二. 而这个是人类进化的结果，目的是为了节能，减少能量的摄入.

AI编程工具正是典型的系统一放大器——它快速给出答案，让人跳过思考过程。久而久之，我发现自己也变得越来越懒得激活系统二了。

这不禁又让我想起我用AI编程的心态转变。


## <span class="section-num">3</span> 心态几经反转 {#心态几经反转}

从网页版本的 ChatGPT 一路用过来，到现在的 Claude Code/Codex, 我对AI编程的心态可以说是几经反转。

Claude Code 这样的 coding agent 可以在输入 prompt 之后，独立生成代码，编译，测试，基本提供一个需求就能独立完成，开头可以说是惊艳。

但是后面我发现生成出来的代码会有过多的冗余，不必要的奇怪逻辑，此外它比较擅长从0生成代码，在已有代码上做修改就很麻烦。

要让减少它生成屎山代码，就需要我来介入 review 把控。

问题在于，让它来生成代码，我来review，我就需要理解它的思路，并且搞懂它的意图；
而当我自己写代码时，思考过程都是在我脑子里面的，就省去了理解意图的步骤，自己写反而会比 review 它的代码来得更快。

如果完全由它自己发挥，只要不到10个需求，我们的代码库就会面目全非，服务炸了还需要我来给它擦屁股，
我也能理解为什么有人说，有了AI反而更累了。

我不是说Agent不好用，有些地方用 Coding Agent 来完成非常顺手：

1.  Debug： 我提供日志，错误信息以及大概的思路，然后让AI顺着我的思路来搜索代码库。
    AI在搜索关键代码方面非常有帮助，毕竟它就擅长搜索，尤其是搜索我不熟悉的第三方库或者是其他团队的内部代码，一般几分钟就能把 bug 找出来；而 bugfix 只需要几行的代码；此外，搜索是个只读操作，AI并不会产生屎山代码。
2.  review 代码：我来review AI 生成的代码很费劲，但是反过来，让AI来review我的代码，就非常简单和有效；
    因为我对自己实现的代码心中有数，所以我一眼就能知道AI的评论是否有道理; 并且人写的代码，变更行数有限，上下文很小，便于发挥AI的特长.
3.  生成验证功能的代码片段：比如要验证某些想法是否可行时，我就会直接让AI来生成代码，反正对质量没有要求。


### <span class="section-num">3.1</span> 矛盾：不懂代码，又如何"vibe coding" {#矛盾-不懂代码-又如何-vibe-coding}

这就有个矛盾的点，如果我不能比AI更懂编程，我又怎么能指导它，写出更贴切的提示词呢？说好的不懂编程也能 vibe coding呢？

我能控制 coding agent 构建出我想象中的应用，但是我不能用它构建出我无法想象的东西，我的想象力和经验其实就是我手中 agent 的上限。

那么，有了AI还要不要读书？

我总会想起《冰与火之歌》： 一同前往绝境长城的路上，雪诺问小恶魔为什么总是在看书，小恶魔答道：

> “我的腿太短，头却太大，总算这脑袋对我还算合适，凭着它我很清楚自己能干什么、不能干什么，它就是我的武器。
>
> 老哥有他的宝剑，劳勃国王有他的战锤，我则有我的脑袋瓜……
>
> 不过人若要保持思路清晰锐利，就得多读书，就好像宝剑需要磨刀石一样。”
>
> 提利昂轻敲书皮，“琼恩·雪诺，这就是为什么我读个不停啰。”

多读书才让自己静下心来学习新的知识，而不是固守在过往的知识，反而对 coding agent 产生越来越强的依赖。


## <span class="section-num">4</span> 后话 {#后话}

书读得足够多，脑子里面有相当的知识量之后，又要怎么去尽量调到系统二来分析和解决问题的呢？

我的做法就是发现 coding agent 出错之后，就去骂它。

因为我发现，在骂它的时候，我脑子就会自动搜索读过的书，寻找相应的论据，让我骂得有理有据，
既趁机触发了系统二，也运用到我读来的知识，还在内心里强化了不能尽信AI的观点, "trust but verify", 可谓是一箭三雕。

当然，这纯属一种自我训练的小伎俩，和老板骂员工的管理逻辑不可同日而语(难怪老板喜欢骂员工), 不过，倒让我理解了为什么批评有时也能激发思考。

### <span class="section-num">4.1</span> 反思才能改善设计 {#反思才能改善设计}

每天上班能用着无限量claude 最新模型的我，对AI的看法也并没有本质性的改变。

我主观感觉在opus 4.8 之后, 虽然模型一直在更新，但是并没有那种 Claude Code 刚出来时, AI乘上 Harness的惊艳.

Agent 擅长做的还是很擅长, 比如搜索，调试，针对特定任务的代码生成等等.

但是与许多视频博主, 写爆款文章的创作者「许愿式」生成的软件不同, 真的有客户使用的软件是有很多限制的。

生成出来的代码, 有客户为之付费后是要维护的，不像这些UP主那样主业是做视频或者发推特，东西做完，有点击量就能丢一边去。

软件维护的负担 AI 并不能帮忙避免, 如果没有经历过这种维护痛苦的人，自然也不会想到如何在设计时尽量减少这样的痛苦，也不会在向AI许愿时有这方面的考虑.

把软件按功能需求实现出来，只是最基本的部分；而非功能性的需求，比如性能，可扩展性，可靠性，兼容性，可维护性，
AI不会帮你考虑到这些痛点的。

这些痛点也并不性感, 就好像童话故事里面，王子和公主在一起之后, 不会有人写婚后要考虑「柴米油盐」的生活.


### <span class="section-num">4.2</span> 软件公司的护城河不是代码 {#软件公司的护城河不是代码}

至于那些说用 [REA](https://github.com/morluto/rea)(reverse engineering anything)来逆向付费软件，甚至SAAS 服务时，我只想说, 这和「写出好代码，就一定有人付费」的想法一样天真.

以Windows 操作系统为例，如果有人用AI逆向出一个免费的 Windows操作系统，你会使用么？

或者换种问法，有人能提供一个免费, 可靠，不差于Windows的操作系统（甚至更优的操作系统），你会使用么？

在30年前就有人做出了这样的操作系统，并由一大群来自全世界的顶尖工程师维护着，
这个操作系统叫Linux，但是它在桌面端的份额也只有3%.

有人逆向出Photoshop，有人逆向出Word办公套件，你会使用么？

甚至不需要逆向，有免费和开源版本的 GIMP 和 LibreOffice，也没有多少人使用嘛。

软件公司的护城河，从来都不是代码；而是经年累月搭建起来的生态，口口相传的品牌，能直达用户的分发渠道等等。


### <span class="section-num">4.3</span> AI改变了软件行业 {#ai改变了软件行业}

但毫无疑问，AI彻底改变了软件编程行业，但现在我们所处的时期有点像是「软件工程」这个概念出现之前的软件开发洪荒时代，
工程师们还没有总结出如何管理AI生成海量代码导致复杂度激增问题的方法论。

相比「软件工程师相信AI是万能的」，更可怕的是「领导层相信AI是万能的」，
觉得AI费用都激增这么多，为什么研发效率没有激增，软件销售收入没有激增？

在AI能以人难以企及的速度来实现想法的当下，做「正确的事」的优先级就变成相当高，但问题在于 ****AI并没有显著改善领导层/产品层做决策的正确率。****

「做这个需求，用户日活就会增加么？来增加订阅量么？」工程师也不知道，反正老板要求拥抱AI，那都试下吧。

在提效的压力，不同的需求同步开发，需求多了，AI生成的代码也多了，代码也Review不过来，老板一直催着快速上线，那就上吧。

用户的日活在各种新特性的堆彻之下，并没有什么新的波澜，但是激增的代码却逐渐失控，各种小故障频发，可靠性下降，客户投诉增多。

面对老板的疑问，客户的投诉，工程师也不知道具体发生了什么问题，只好用AI去排查AI生成的代码，再把AI排查出来的结果告知老板。

这样的场景我已经在工作中见得越来越多了。

感触是由来以久，但仿佛是为了印证我的看法，在写下这段文字的2天前，微软的 Outlook 365以及其他Exchange服务 竟然挂了超过20个小时，如此重要的服务全球宕机如此长的时间，真的是难以置信。

更难以置信的是，过了12个小时，他们发出来的公告表明，他们还不知道发生了什么问题，也不知道怎么处理：

### <span class="section-num">4.4</span> 人人都在FOMO {#人人都在fomo}

此外，我觉得AI很大程度上剥夺了初级工程师成长的机会。

我见到很多的毕业生使用AI生成代码非常熟练，
但问及相关的设计，尤其是为什么要这么设计的时候，他们大多是把问题转述给AI，然后把AI的答案复述出来。

AI的答案有时候似是而非，他们又没有足够的经验去分辨，就容易信以为真。

他们失去了宝贵的犯错，改错再反思的机会。

问题又来了, Who cares?

从公司高层，到中层，再到底层，人人都在FOMO(fear of missing out)：

高层担心错过AI这波浪潮，成为新时代的柯达；

中层担心自己没有践行好高层拥抱AI的策略，执行不力；

底层担心自己的饭碗，在一波「降本增效」中丢失，老板让我干啥就干啥，不就用AI写代码嘛，让我用AI直接push代码到生产环境我都无异议。


### <span class="section-num">4.5</span> 许愿也要知道自己要什么 {#许愿也要知道自己要什么}

对于使用AI, 我个人的观点始终都是，你要先明确知道要什么，才能创造出什么。

你不能期待给AI一个 prompt：

> 给我生成一个软件，能赚钱，不能有bug

它就能给你一台印钞机

要知道自己要什么，就需要不断思考，学习与实践；那样的人，又怎么会被AI取代呢。

所以你是AI的反对者，就像纺织工人反对蒸汽机那样？

恰好相反，我是AI的拥护者，AI绝对能帮我提高生产效率，我只是那些不清楚AI能力边界的「AI万能论」的质疑者。
